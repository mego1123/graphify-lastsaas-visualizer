    26→### What the interface analyzer does
    27→

    33→3. Parses every `type Y struct { ... }` declaration and every method bound
    34→   to it (both value receivers `func (s Y) M()` and pointer receivers

    49→                                       [--include-tests]

    52→### What the middleware analyzer does
    53→
    54→1. Walks every `.go` file and detects middleware usage patterns:
    55→   - `router.Use(...)` / `api.Use(...)` / `r.Use(...)` — gorilla/mux style
    56→   - `middleware.Func(...)` factory calls (e.g. `middleware.RequireRole(role)`)
    57→   - Method-style middleware: `authMiddleware.RequireAuth`, `metricsCollector.Middleware(...)`
    58→   - Manual nesting: `handler := m1(m2(m3(finalHandler)))`
    59→   - `http.Handler` wrapping (`c.Handler(...)`, `http.HandlerFunc(...)`)
    60→   - `rateLimiter.RateLimitHandler(config, keyFunc, handler)` — per-route
    61→     rate-limit pattern
    62→2. Reconstructs execution order: outermost wrapper runs first; innermost is
    63→   the terminal handler.
    64→3. For each middleware definition, inspects the function body and decides:
    65→   - **runs_before** — does work before calling `next.ServeHTTP`
    66→   - **runs_after** — does work after `next.ServeHTTP` (or via `defer`)
    67→   - **short_circuits** — may return without calling `next.ServeHTTP`
    68→     (proactive request rejection). Detection uses `http.Error(...)` /
    69→     `WriteHeader(http.StatusXXX)` calls that are NOT inside a `defer`
    70→     block, so panic-recovery middleware like `Recovery` is correctly
    71→     classified as *not* short-circuiting.
    72→4. Emits a visual chain for every router, e.g.:
    73→   ```
    74→   Request → Recovery → BodySizeLimit → SecurityHeaders → CORS → Metrics → Router (Handler) → Response
    75→   ```
    76→   with ✋ markers on short-circuiting middleware.
    77→5. Per-router stacks (combining multiple `.Use(...)` calls on the same
    78→   router in declaration order).
    79→6. Rate-limit site inventory — every endpoint wrapped with
    80→   `RateLimitHandler` is listed.
    81→7. Emits both Markdown (`MIDDLEWARE.md`) and JSON (`middleware.json`).
    82→
    83→CLI:
    84→```
    85→python scripts/graphify_middleware.py [path] [--out report.md] [--json]
    86→                                       [--include-tests]
    87→```

   171→
   172→**Date**: 2026-08-05
   173→**Scope**: Build a Python analyzer that audits Go source code for error
   174→handling patterns and persist its reports to `/home/z/my-project/public/`.
   175→
   176→### Files created
   177→
   178→- `scripts/graphify_errors.py` — Go error handling pattern auditor
   179→
   180→### Outputs written to `public/`
   181→
   182→- `error-audit.json` (≈ 320 KB) — full machine-readable audit report
   183→- `ERROR_AUDIT.md` (≈ 230 KB) — human-readable audit summary
   184→
   185→### What the analyzer does
   186→
   187→1. Walks every `.go` file (excluding `vendor/`, `node_modules/`, `.git/`,
   188→   `graphify-out/`, `testdata/`) under the target path. Single-file and
   189→   directory paths are both supported.
   190→2. For each file, masks out string literals and comments (preserving
   191→   length and newlines) so brace/paren matching is robust against
   192→   braces appearing inside strings or comments.
   193→3. Locates every named top-level function and method declaration via
   194→   regex + brace matching, building per-function `(start_line, end_line)`
   195→   ranges so each finding can be attributed to its containing function.
   196→4. Detects four classes of error-handling constructs:
   197→   - **`if X != nil { ... }` blocks** — located via `IF_NIL_RE`, body
   198→     extracted via brace matching, then classified into one of:
   199→       - `proper_handling` (LOW) — body returns `err` (directly or via
   200→         `fmt.Errorf("...: %w", err)` / `errors.Wrap(err, ...)`), OR
   201→         terminates with `os.Exit(non-zero)` / `log.Fatal*` / `t.Fatal*`
   202→         after reporting the error.
   203→       - `panic_on_error` (MEDIUM) — body calls `panic(...)`.
   204→       - `logged_only` (MEDIUM) — body has no `return`, but reports the
   205→         error via `log.*` / `slog.*` / `fmt.Print*` / `respondWithError`
   206→         / `http.Error` / `t.Error*` (i.e. error is acknowledged but not
   207→         propagated).
   208→       - `swallowed` (HIGH) — empty body, or body that returns without
   209→         `err` (dropping the error info), or body that does anything else
   210→         without propagating/reporting.
   211→   - **Ignored errors** — `result, _ := someFunc(...)` patterns where the
   212→     last return value is discarded with `_`. `for k, _ := range m` is
   213→     excluded (map iteration idiom).
   214→   - **Missing error checks** — statement-form method calls (not
   215→     assigned, not preceded by `defer`/`go`) to a known error-returning
   216→     method such as `Close`, `Write`, `Read`, `InsertOne`, `UpdateOne`,
   217→     `DeleteOne`, `BulkWrite`, `Marshal`, `Unmarshal`, `Encode`, `Decode`,
   218→     `Parse`, `Exec`, `Commit`, `Ping`, etc. The **outermost** call in a
   219→     chain is examined (e.g. `collection.FindOne(...).Decode(&x)` is
   220→     attributed to `Decode`, not `FindOne`). Free-function calls (no `.`
   221→     receiver) are skipped to avoid noise from custom helpers.
   222→   - **Panic on error** — flagged separately so non-`init()` panics can
   223→     be reviewed (per the spec, panicking is acceptable in `init()` but
   224→     risky elsewhere).
   225→5. Skips lines inside `if X != nil { ... }` blocks for the missing-check
   226→   scan so the same error site isn't double-counted.
   227→6. For each finding, records: file (relative to project root), line,
   228→   end_line, containing function, pattern type, severity, code snippet
   229→   (capped at 6 lines), and a note explaining the heuristic that fired.
   230→7. Test files (`*_test.go`) are scanned separately; only their aggregate
   231→   statistics appear in the report (test-file findings are not included
   232→   in the detailed findings list, per the spec).
   233→
   234→### CLI
   235→
   236→```
   237→python graphify_errors.py [path] [--out report.md] [--json] [--include-tests]
   238→```
   239→
   240→- `path` — file or directory to audit (default: `.`).
   241→- `--out report.md` — write markdown report to this path in addition to
   242→  the default `public/ERROR_AUDIT.md`.
   243→- `--json` — print the JSON report to stdout.
   244→- `--include-tests` — reserved (test-file findings always excluded from
   245→  the detailed list; their stats are always reported in the summary).

   247→The script always writes `public/error-audit.json` and

   300→### Implementation notes
   301→
   302→- The script is pure-Python (no `tree-sitter` dependency, unlike
   303→  `graphify_verify.py`); it relies on a custom string/comment masker
   304→  plus brace matching, which is sufficient for Go's relatively regular
   305→  syntax.
   306→- The `extract_outermost_method` helper walks a single source line,
   307→  tracks `()` / `[]` / `{}` depth, and returns the **last** top-level
   308→  call's method name — this correctly handles chained calls like
   309→  `client.Database("x").Collection("y").InsertOne(ctx, doc)` by
   310→  attributing the call to `InsertOne` (the actual error-returning call),
   311→  not `Database` or `Collection` (which return builder types).
   312→- Free-function calls are skipped from the missing-check scan because
   313→  the auditor cannot infer their signatures without type information.
   314→  This avoids false positives like `apierror.Write(w, status, ...)` —
   315→  a void package-level helper that happens to share a name with
   316→  `io.Writer.Write`.
   317→- `WriteString` is deliberately **not** in the error-returning set:
   318→  `strings.Builder.WriteString` and `bytes.Buffer.WriteString` always
   319→  return a nil error, and including it produced 64 false positives in
   320→  `internal/api/handlers/docs.go` alone (the OpenAPI HTML generator
   321→  uses `sb.WriteString(...)` extensively).
   322→- The classifier recognizes several legitimate "non-propagating but
   323→  acceptable" patterns and treats them as `proper_handling`:
   324→  - `os.Exit(non-zero)` after printing the error (CLI termination).
   325→  - `log.Fatal*` (calls `os.Exit(1)` internally).
   326→  - `t.Fatal*` (test termination — fails the test immediately).
   327→  - `return fmt.Errorf("...: %w", err)` / `errors.Wrap(err, ...)`
   328→    (error wrapping).
   329→  Returning a *new* error without the original (e.g.
   330→  `return errors.New("oops")`) is classified as `swallowed` because
   331→  the original error info is dropped.
   332→- The HTTP-handler pattern
   333→  `if err != nil { respondWithError(w, status, msg); return }` is
   334→  classified as `logged_only` (MEDIUM) rather than `swallowed` (HIGH)
   335→  because the error IS acknowledged (it triggers the error response)
   336→  even though the original `err` value isn't propagated. The
   337→  `ERROR_REPORT_RE` regex covers `respondWithError`, `http.Error`,
   338→  `writeError`, `sendError`, `c.JSON`, and similar response helpers.

   363→## Task ID: fix-auditor — Eliminate swallowed-error false positives
   364→
   365→**Date**: 2026-08-05
   366→**Scope**: Refactor `scripts/graphify_errors.py` so the "swallowed" classifier
   367→recognises the legitimate Go error-handling patterns the `lastsaas` backend
   368→uses, then re-run the audit and refresh the public reports.
   369→
   370→### Problem
   371→
   372→The previous auditor reported **140 "swallowed" errors** in the `lastsaas`
   373→backend, but only ~6 of those were genuinely broken. The remaining ~134
   374→were valid Go patterns the classifier didn't recognise as "handled":
   375→
   376→- `if err != nil { slog.Warn(...); return }` — error logged then early-return
   377→- `if err != nil { http.Redirect(...); return }` — OAuth callback redirects
   378→  the browser to a login-error URL
   379→- `if err != nil { respondWithError(w, ...); return }` — HTTP handler
   380→  reports the error to the client and short-circuits
   381→- `if err != nil { page = 1 }` — input clamping (parse-error → default)
   382→- `if err != nil { delivery.Success = false; ... }` — failure flagging on
   383→  a struct field
   384→- `if err != nil { if err == mongo.ErrNoDocuments { ... } }` — sentinel
   385→  error type check (expected "not found" branch)
   386→- `if err != nil { slog.Warn(...); continue }` — batch-processing skip
   387→- `if err != nil { fmt.Fprintf(os.Stderr, ...); return }` — CLI tool logs
   388→  the error to stderr and exits the function
   389→
   390→The classifier was checking only for `return err` / `os.Exit` / `log.Fatal`
   391→/ `t.Fatal` as "proper", and `log.*` / `slog.*` / `fmt.*` calls **only when
   392→there was no `return`** in the body. Any body with a bare `return` or
   393→`return <non-err>` fell through to the `has_return → swallowed` branch
   394→without checking whether the error had been acknowledged in some other
   395→way.
   396→
   397→### Files changed
   398→
   399→- `scripts/graphify_errors.py` — added new regex patterns for valid
   400→  handler detection, refactored `classify_err_body` to check them BEFORE
   401→  the `has_return → swallowed` branch, made `RETURN_ERR_RE` case-insensitive
   402→  so it also catches `return res.Err()` / `return cursor.Err()`, and
   403→  updated the module docstring + markdown methodology section.
   404→
   405→### Code changes
   406→
   407→#### New regex constants
   408→
   409→```python
   410→# Explicit "logging" patterns. Used to reclassify what would otherwise be
   411→# `swallowed` as `logged_only` (MEDIUM). `fmt.Errorf` is intentionally
   412→# excluded — it constructs a new error rather than logging one.
   413→SLOG_LOG_RE  = r'\bslog\.(?:Warn|Error|Info|Debug)(?:ln|f)?\s*\('
   414→LOG_PRINT_RE = r'\blog\.(?:Print|Printf|Println|Fatal*|Panic*)\s*\('
   415→FMT_PRINT_RE = r'\bfmt\.(?:Print*|Fprint*|Sprint*)\s*\('     # excludes Errorf
   416→STDERR_FMT_RE = r'\bfmt\.F(?:printf|println|print)\s*\(\s*os\.Stderr\b'
   417→
   418→# Proper-handler patterns — body takes a corrective/terminal action even
   419→# when the original `err` is not propagated.
   420→HTTP_REDIRECT_RE = r'\bhttp\.Redirect\s*\('
   421→ERRNO_DOCS_RE    = r'\b(?:mongo\.)?ErrNoDocuments\b'
   422→CONTINUE_RE      = r'\bcontinue\b'
   423→ASSIGNMENT_RE    = r'^[ \t]*\w[\w.]*\s*=(?!=)'   # var = value, obj.field = value
   424→                                                 # excludes == and :=
   425→```
   426→
   427→#### `RETURN_ERR_RE` made case-insensitive
   428→
   429→The original `r'\breturn\b[^;]*\berr\b'` only matched lowercase `err`, so
   430→`return fmt.Errorf("...: %w", res.Err())` (which wraps the error properly
   431→via `%w`) was being misclassified as `swallowed` by the
   432→`RETURN_NEW_ERR_RE` fallback. Adding `re.IGNORECASE` lets it match `Err`
   433→too while still requiring `err` to be a complete word (so `ferrisWheel`
   434→isn't matched).
   435→
   436→#### `classify_err_body` refactor
   437→
   438→The new classification order (each step short-circuits):
   439→
   440→1.  Empty body                                    → `swallowed`
   441→2.  `panic(...)`                                  → `panic_on_error`
   442→3.  Terminal exit (`os.Exit(non-zero)`, `log.Fatal*`, `t.Fatal*`) → `proper_handling`
   443→4.  `return ...err...` (case-insensitive)         → `proper_handling`
   444→5.  **Proper-handler patterns** (any of):
   445→    - `http.Redirect(...)`
   446→    - `respondWithError(...)` / `http.Error(...)` / `writeError(...)` / etc.
   447→    - `mongo.ErrNoDocuments` / `ErrNoDocuments` check
   448→    - `continue` statement (batch processing)
   449→    - Assignment to a variable or struct field
   450→      (`page = 1`, `delivery.Success = false`, …)  → `proper_handling`
   451→6.  **Logging patterns** (any of):
   452→    - `slog.Warn/Error/Info/Debug(...)`
   453→    - `log.Print*`/`Fatal*`/`Panic*(...)`
   454→    - `fmt.Print*`/`Fprint*`/`Sprint*(...)`
   455→      (excludes `fmt.Errorf` — that's error construction)
   456→    - `fmt.Fprint*(os.Stderr, ...)`               → `logged_only`
   457→7.  `return` (bare or new error like
   458→    `return errors.New("oops")`)                  → `swallowed`
   459→8.  `t.Error*` (no return, no other handler)      → `logged_only`
   460→9.  Body consists ONLY of logging calls
   461→    (fallback `LOG_CALL_RE` sweep)                → `logged_only`
   462→10. Anything else                                 → `swallowed`
   463→
   464→The key change is that steps 5 and 6 are checked BEFORE the `has_return`
   465→branch. This is what eliminates the bulk of the false positives: bodies
   466→like `slog.Warn(...); return` and `http.Redirect(...); return` are now
   467→recognised as acknowledged/handled rather than swallowed.
   468→
   469→**Important behavioural change**: `respondWithError(...)` / `http.Error(...)`
   470→were previously classified as `logged_only` (MEDIUM); they are now
   471→`proper_handling` (LOW) per the spec — the error IS reported to the
   472→client and the request IS short-circuited, which is a legitimate
   473→production handling pattern for HTTP handlers.

   600→### What the N+1 analyzer does
   601→
   602→1. Walks every `.go` file (excluding `*_test.go` by default) under the
   603→   target path, masks out string literals and comments (preserving length
   604→   and newlines), then locates every loop header
   605→   (`for ... range ...`, `for init; cond; post { ... }`,
   606→   `for cond { ... }`, `for { ... }`) and finds the matching `}` via
   607→   depth-counting brace matching.
   608→2. For each loop body (lines `start_line+1` to `end_line`), scans every
   609→   line for a MongoDB collection method call —
   610→   `Find`, `FindOne`, `InsertOne`, `InsertMany`, `UpdateOne`,
   611→   `UpdateMany`, `ReplaceOne`, `DeleteOne`, `DeleteMany`, `Aggregate`,
   612→   `CountDocuments`, `EstimatedDocumentCount`. Option-builder calls
   613→   (`options.Find()`, `options.FindOne()`) are skipped.
   614→3. For each DB-op line inside a loop body, resolves the collection via
   615→   three strategies: literal `db.Collection("name")`, accessor call
   616→   `m.Users()` (resolved via the codebase's accessor map), or aliased
   617→   local variable `col := m.Users()`. Also recognises dynamic collection
   618→   names (`db.Collection(name)` where `name` is a variable) and labels
   619→   them `dynamic:<varname>`.
   620→4. Records for each finding: file, loop start line, loop close line,
   621→   call line (where the DB op actually appears), containing function,
   622→   loop kind (`range` / `three-form` / `condition` / `infinite`),
   623→   loop variable, MongoDB operation, collection, code snippet, a
   624→   context-specific remediation suggestion (different for reads vs
   625→   writes vs deletes), and a risk classification.
   626→5. **Risk**: HIGH for queries in user-facing handler code; MEDIUM for
   627→   admin/CLI/batch paths (still bad, but lower blast radius).
   628→6. Emits both Markdown (`N_PLUS_1.md`) and JSON (`n-plus-1.json`).
   629→
   630→### What the missing-index analyzer does
   631→
   632→1. **Index inventory.** Walks every `.go` file and parses every
   633→   `mongo.IndexModel{ Keys: bson.D{...}, Options: ... }` declaration.
   634→   Two patterns are recognised:
   635→
   636→   - The slice-of-anonymous-struct form used by
   637→     `internal/db/mongodb.go::ensureIndexes()`:
   638→
   639→       ```go
   640→       indexes := []struct {
   641→           collection string
   642→           models     []mongo.IndexModel
   643→       }{
   644→           {
   645→               "users",
   646→               []mongo.IndexModel{
   647→                   {Keys: bson.D{{Key: "email", Value: 1}}, Options: ...},
   648→                   ...
   649→               },
   650→           },
   651→           ...
   652→       }
   653→       ```
   654→
   655→     The collection comes from the string literal that precedes each
   656→     `[]mongo.IndexModel{` block. Individual entries are extracted by
   657→     iterating top-level `{...}` blocks (brace matching, not regex) and
   658→     splitting each entry on the first top-level `,` to separate `Keys:`
   659→     from `Options:`. This correctly handles the nested braces in
   660→     `bson.D{{Key: "f", Value: 1}}` and the chained `SetUnique(true).SetSparse(true)`
   661→     options.
   662→
   663→   - The standalone `mongo.IndexModel{...}` form used by
   664→     `internal/middleware/ratelimit.go`:
   665→
   666→       ```go
   667→       coll.Indexes().CreateOne(ctx, mongo.IndexModel{
   668→           Keys:    bson.D{{Key: "expiresAt", Value: 1}},
   669→           Options: options.Index().SetExpireAfterSeconds(0),
   670→       })
   671→       ```
   672→
   673→     The collection is resolved by binary-searching backwards for the
   674→     nearest preceding collection-binding site (`db.Collection("name")`
   675→     literal, alias variable, or a `Collection("name").Indexes()` call
   676→     on the same expression).
   677→
   678→2. **Query scan.** Walks every `.go` file and locates each MongoDB
   679→   collection method call. The first-argument filter is parsed from the
   680→   `bson.M{}` / `bson.D{}` literal, with a multi-line look-ahead window
   681→   so multi-line filter literals are captured. InsertOne/InsertMany/
   682→   Aggregate are skipped (no filter to check).
   683→3. **Coverage check.** For each query the filter fields are compared
   684→   against the collection's index inventory. A query is covered if ANY
   685→   of: it filters by `_id` (always indexed by MongoDB), it filters by a
   686→   single-field index, or it filters by the leading field of a compound
   687→   index. Queries with no covering index are flagged as `no_index`.
   688→4. **Spec-required check.** Each query is also checked against a small
   689→   SaaS-domain rule set (`REQUIRED_INDEX_FIELDS`): `email` on `users`,
   690→   `slug` on `tenants`, `token` on `invitations` / `verification_tokens`
   691→   / `auth_codes`, `tenantId` on multi-tenant collections, `userId` on
   692→   membership/log/token collections, etc. Queries that filter on a
   693→   spec-required field that isn't indexed are flagged as `missing_required`.
   694→5. **Multi-tenant hygiene.** Empty-filter queries on multi-tenant
   695→   collections (`tenant_memberships`, `audit_log`, `system_logs`,
   696→   `telemetry_events`, `usage_events`, `financial_transactions`,
   697→   `messages`, `api_keys`, `webhooks`, `webhook_deliveries`,
   698→   `sso_connections`, `announcements`) are flagged as
   699→   `multi_tenant_unfiltered` — full collection scans that risk
   700→   cross-tenant data leaks.
   701→6. **Risk**: HIGH for queries on large collections (logs, events,
   702→   telemetry, audit, deliveries, metrics) without a covering index, and
   703→   for queries on spec-required fields without an index. MEDIUM for
   704→   small/static-data collections without coverage and for multi-tenant
   705→   empty-filter queries on small collections.
   706→7. Emits both Markdown (`MISSING_INDEXES.md`) and JSON
   707→   (`missing-indexes.json`). The report includes a full **index
   708→   inventory** table showing every declared index, its fields, leading
   709→   field, and unique/TTL/sparse flags.
   710→
   711→### What the dead-code analyzer does
   712→
   713→1. Walks every non-test `.go` file under the target path, parses every
   714→   `func [recv] Name(...)` declaration (free functions and methods), and
   715→   finds the body's line range via brace matching.
   716→2. **Exclusions** (functions never reported as dead):
   717→   - `main()` and `init()` — Go entry points.
   718→   - `Test*`, `Benchmark*`, `Fuzz*`, `Example*` — testing framework
   719→     entry points.
   720→   - Well-known interface-satisfying methods that may be invoked via
   721→     interface dispatch or reflection: `String`, `Error`, `Unwrap`,
   722→     `Is`, `As`, `MarshalJSON`, `UnmarshalJSON`, `MarshalText`,
   723→     `Read`/`Write`/`Close`/`Flush`, `Len`/`Less`/`Swap`,
   724→     `ServeHTTP`, `Value`/`Scan`, `Format`, `Deadline`/`Done`/`Err`,
   725→     etc.
   726→   - Stub functions whose body is just `panic("not implemented")` /
   727→     `panic("TODO")` / `panic("unreachable")`.
   728→3. For every remaining function, the codebase is searched for
   729→   whole-word references to the function name across ALL `.go` files
   730→   (including `*_test.go` — tests are legitimate external callers).
   731→   String literals and comments are masked out before searching so
   732→   doc-comment mentions don't count as references.
   733→4. **Unexported function**: reported as dead if it has zero references
   734→   anywhere outside its own definition line.
   735→5. **Exported function**: reported as dead if no OTHER file references
   736→   it. Same-file references don't count because removing the function
   737→   would also remove those callers — they're part of the same dead
   738→   subtree.
   739→6. Each finding records: function name, file, line, end_line,
   740→   function_kind (`exported` / `unexported`), receiver type (for
   741→   methods), `external_refs` (number of other files referencing it),
   742→   `same_file_refs` (number of references in same file outside the
   743→   definition), `total_refs`, code snippet (from raw source, not
   744→   masked), severity (always LOW), and a note.
   745→7. Emits both Markdown (`DEAD_CODE_GO.md`) and JSON (`dead-code-go.json`).

   895→  `db.Collection(<var>)` are labelled `dynamic:<varname>` so the report
   896→  is informative rather than just `<unknown>`.
   897→- The missing-index analyzer's index parser was tricky because
   898→  `ensureIndexes()` uses a slice of anonymous structs with a
   899→  `[]mongo.IndexModel{...}` slice field per collection. The first
   900→  attempt (regex-only) failed because the nested braces in
   901→  `bson.D{{Key: "f", Value: 1}}` confuse any regex that tries to match
   902→  a single entry's `{...}` block. The fix is a two-stage parse: regex
   903→  to find each `"<coll>", []mongo.IndexModel{...}` block, then a small
   904→  brace-matching iterator (`_iter_top_level_entries`) to walk each
   905→  `{Keys: ..., Options: ...}` entry inside, then a depth-aware
   906→  splitter (`_extract_keys_and_options`) to separate the two halves on
   907→  the first top-level `,`. This correctly handles compound indexes
   908→  (`bson.D{{Key: "tenantId", Value: 1}, {Key: "createdAt", Value: -1}}`)
   909→  and the chained options (`SetUnique(true).SetSparse(true)`).

   911→  rule: a query is covered if ANY filter field is the leading field of
   912→  any index (single-field or compound). MongoDB can use a compound
   913→  index for a query that filters only on its leading field, but NOT
   914→  for a query that filters only on a trailing field. The script also
   915→  treats `_id` as an implicit single-field index (MongoDB always
   916→  creates it), so any query that filters by `_id` (alone or with other
   917→  fields) is automatically covered — this eliminated ~120 false
   918→  positives on `UpdateOne(filter={"_id": ..., "field": ...})` patterns
   919→  that update a single document by ID.
   920→- The dead-code analyzer keeps two source representations per file:
   921→  masked (for reference search — so identifiers in strings/comments
   922→  don't count) and raw (for snippet rendering). Snippets originally
   923→  came out garbled because they were being sliced from the masked
   924→  text; switched to raw and the snippets now show real source.
   925→- The dead-code analyzer conservatively excludes well-known
   926→  interface-satisfying methods (`String`, `Error`, `MarshalJSON`,
   927→  `ServeHTTP`, `Len`/`Less`/`Swap`, etc.) because they may be called
   928→  via interface dispatch or reflection, which a name-based grep can't
   929→  detect. This trades a few false negatives (some genuinely dead
   930→  `String()` methods exist) for zero false positives — matching the

  1160→### Implementation notes
  1161→
  1162→- The auditor is **pure-Python** (no tree-sitter or Go AST dependency),
  1163→  following the convention established by `graphify_errors.py` and
  1164→  `graphify_db_queries.py`. It relies on a custom string/comment masker
  1165→  plus brace matching, which is sufficient for Go's relatively regular
  1166→  syntax.
  1167→- **Masking strategy**: the masker replaces string literals (raw,
  1168→  interpreted, rune) and comments (line, block) with spaces — preserving
  1169→  length and newlines. Two parallel text representations are maintained:
  1170→  - `masked` — used for OP_RE matching (so `.Find(` inside a string
  1171→    literal doesn't false-match) and for brace/paren depth tracking in
  1172→    `extract_call_args` and `_collect_brace_window` (so braces inside
  1173→    strings don't prematurely close a block).
  1174→  - `raw` — used for slicing argument text and extracting filter fields
  1175→    (so the bson string keys `"tenantId"`, `"_id"`, etc. are visible to
  1176→    the field-extraction regexes).
  1177→  The two representations have identical length and newline positions,
  1178→  so the same character indices work for both.
  1179→- **Variable filter tracing**: the auditor tracks three kinds of
  1180→  per-function variable assignments:
  1181→  - **Collection aliases** (`col := h.db.Users()`) — used to resolve
  1182→    `col.Find(...)` calls.
  1183→  - **Filter variables** (`filter := bson.M{...}` + dynamic additions
  1184→    `filter["tenantId"] = ...`) — used to resolve
  1185→    `h.db.X().Find(ctx, filter)` calls. The dynamic-addition regex
  1186→    runs on the RAW line (not masked) because the string key must be
  1187→    visible.
  1188→  - **Pipeline variables** (`pipeline := []bson.M{...}` /
  1189→    `mongo.Pipeline{...}` / `bson.A{...}`) — used to resolve
  1190→    `h.db.X().Aggregate(ctx, pipeline)` calls. The `$match` stage
  1191→    extraction uses `find_block_end` to locate the closing brace of
  1192→    each `bson.M{...}` block within the `$match` stage, then delegates
  1193→    to `extract_filter_fields_from_text`.
  1194→  - **Struct-typed variables** (`invitation := models.Invitation{...}`)
  1195→    — used to resolve `InsertOne(ctx, invitation)` calls. The struct's
  1196→    bson field tags are looked up in the struct-field index to
  1197→    determine whether `tenantId` is declared.
  1198→- **`EstimatedDocumentCount`**: included in `ALL_OPERATIONS` so it's
  1199→  detected, but classified specially (`filter_source = "no-filter"`)
  1200→  because it takes no filter argument. On a tenant-scoped collection
  1201→  it's HIGH risk (leaks the total document count across all tenants);
  1202→  on a global collection it's MEDIUM. All 3 occurrences in the
  1203→  codebase are on exempt collections (`users`, `tenants`, `system_logs`).
  1204→- **`UpdateByID`**: classified as `safe_key_filter = True` because the
  1205→  2nd argument is the document `_id` (globally unique). The
  1206→  `filter_fields` list is set to `["_id"]` so the report shows the
  1207→  filter clearly.
  1208→- **`BulkWrite`**: flagged with `filter_source = "bulk-write-models"`
  1209→  and a note explaining that individual WriteModel operations cannot
  1210→  be analysed statically. No BulkWrite calls were found in the
  1211→  codebase.
  1212→- **`InsertMany`**: the 2nd argument is a slice of documents. The
  1213→  auditor extracts fields from any inline `bson.M{}` literals in the
  1214→  slice. If the documents are struct values, the struct fields can't
  1215→  be easily analysed (each slice element would need its own struct
  1216→  resolution) — flagged with a note. 2 `InsertMany` calls found, both
  1217→  on `telemetry_events` (which legitimately has no `tenantId`).
  1218→- The **safe-key heuristic** is conservative: it only includes truly
  1219→  globally-unique identifiers (`_id`, `slug`, `tokenHash`, `keyHash`,
  1220→  `code`, `eventId`, `credentialId`, `machineId`, `email`, `name`,
  1221→  `invoiceNumber`, `familyId`). It does NOT include `userId` (which is
  1222→  unique per user but a user can belong to multiple tenants) or `key`
  1223→  (which is a generic name that happens to be unique in
  1224→  `branding_assets` but might not be in other collections). Reviewers
  1225→  can dismiss false positives based on context.
  1226→- The report separates **real violations** (no safe key, need review)
  1227→  from **safe-key violations** (likely false positives) so reviewers
  1228→  can triage efficiently. The per-file section at the end lists every
  1229→  query (including OK and MEDIUM) for completeness.

  1306→### What was causing the false positives
  1307→
  1308→The original auditor applied a single test: "Does the filter contain
  1309→`tenantId`?" If not, it flagged the query as a violation (HIGH for reads,
  1310→CRITICAL for writes). This caught 226 queries that were all legitimate
  1311→because they fell into one of these context categories:
  1312→
  1313→1. **Global-by-design collections** (147 queries) — Collections whose Go
  1314→   struct does NOT declare a `tenantId` bson field. Examples: `webhooks`,
  1315→   `plans`, `system_nodes`, `event_definitions`, `branding_assets`,
  1316→   `api_keys`, `custom_pages`, `credit_bundles`, `config_vars`,
  1317→   `announcements`. The previous auditor only had a 5-element hardcoded
  1318→   exempt list (`tenants`, `plans`, `system_config`, `system_logs`,
  1319→   `users`); it now derives the global-collection set automatically by
  1320→   walking every `type X struct { ... }` declaration and checking the
  1321→   bson field tags.
  1322→
  1323→2. **Admin handlers** (179 queries) — Handlers registered on `adminAPI`
  1324→   / `adminWrite` / `adminOwner` in `cmd/server/main.go`. These are
  1325→   root-tenant + user-role routes that legitimately see ALL tenants.
  1326→   Examples: `ListUsers`, `GetTenant`, `ListPlans`, `ListLogs`,
  1327→   `AdminGetMetrics`, `ListAPIKeys`, `ListWebhooks`,
  1328→   `ListEventDefinitions`. The auditor now parses main.go to extract the
  1329→   handler-function names registered on each router variable, and treats
  1330→   any query inside an admin handler as MEDIUM (admin sees all tenants
  1331→   by design).
  1332→
  1333→3. **CLI tools** (76 queries) — Files under `cmd/lastsaas/` are not
  1334→   HTTP request handlers — they're CLI commands with no request context.
  1335→   The auditor now detects these by path and downgrades them.
  1336→
  1337→4. **Background system tasks** (28 queries) — Functions like
  1338→   `flushLoop`, `tryAcquireOrRenew`, `heartbeat`, `registerNode`,
  1339→   `dispatch`, `deliverWithRetry`, `collectDaily`,
  1340→   `aggregateDailyPoints`, `handleCheckoutCompleted`. They have no
  1341→   request context and therefore no `tenantId` available — they operate
  1342→   on system-wide collections by design.
  1343→
  1344→5. **Public endpoints** (14 queries) — Handlers like `ListPublic`,
  1345→   `ListPublicPages`, `ListBundlesPublic`, `GetBranding`, `ServeAsset`,
  1346→   `GetPublicPage`, `HandleWebhook` (Stripe signature-verified), and
  1347→   `TrackAnonymous` (anonymous telemetry). No auth — published content
  1348→   visible to everyone.
  1349→
  1350→6. **Test utilities** (10 queries) — `internal/testutil/testutil.go`
  1351→   helpers that reset/clean test databases between test runs. Not
  1352→   production code.
  1353→
  1354→7. **User-scoped collections with userId filter** (6 queries) —
  1355→   Collections whose struct has a `userId` bson field (e.g.
  1356→   `refresh_tokens`, `verification_tokens`, `messages`,
  1357→   `tenant_memberships`, `financial_transactions`, `system_logs`,

  1385→### How the new heuristics are implemented
  1386→
  1387→#### 1. Collection→struct resolver
  1388→
  1389→`build_collection_struct_map(accessor_map, struct_fields)` walks each
  1390→collection name returned by an accessor method, derives the candidate
  1391→Go struct name using a snake_case → PascalCase heuristic with plural
  1392→handling (`ies` → `y`, trailing `s` stripped), and confirms it exists
  1393→in the struct-field index. Hardcoded overrides handle acronym
  1394→capitalisation (`api_keys` → `APIKey`, `oauth_states` → `OAuthState`,
  1395→`sso_connections` → `SSOConnection`, `webauthn_credentials` →
  1396→`WebAuthnCredential`, `counters` → `InvoiceCounter`).
  1397→
  1398→`build_user_scoped_collections(csm, sf)` returns the set of
  1399→collections whose struct has a `userId` bson field — for these, a
  1400→`userId` filter is a valid scope.
  1401→
  1402→`build_global_collections(csm, sf)` returns the set of collections
  1403→whose struct does NOT declare a `tenantId` field — these are GLOBAL BY
  1404→DESIGN.
  1405→
  1406→#### 2. Route classifier (parses main.go)
  1407→
  1408→`build_route_classifier(repo_root)` finds `cmd/server/main.go`, walks
  1409→every `router.HandleFunc("/path", HANDLER).Methods("VERB")` call, and
  1410→maps the handler function name to a route scope based on the router
  1411→variable:
  1412→
  1413→- `adminAPI`, `adminWrite`, `adminOwner` → admin (91 handlers)
  1414→- `tenantAPI`, `tenantSettingsRouter`, `inviteRouter`, `removeRouter`,
  1415→  `ownerRouter`, `usageAPI`, `telemetryAPI`, `billingAPI`,
  1416→  `billingOwner` → tenant (18 handlers)
  1417→- `guarded`, `protectedAuth`, `api`, `router` → auth (32 handlers) or
  1418→  public (12 handlers — split via the `PUBLIC_ENDPOINT_FUNCS` set)
  1419→
  1420→The regex uses the RAW source text (so the `"/path"` string literal is
  1421→visible), but paren-depth tracking uses the MASKED text (so parens
  1422→inside strings don't confuse the splitter). For wrapped handlers like
  1423→`rateLimiter.RateLimitHandler(..., handler.Foo,)`, the LAST
  1424→`handler.Foo` reference is taken as the actual handler.
  1425→
  1426→#### 3. ADMIN_SERVICE_FUNCS set
  1427→
  1428→The route classifier only catches HTTP handler names registered on
  1429→routers — it doesn't catch the underlying service methods they
  1430→delegate to. For example, `pmHandler.GetFunnel` (registered on
  1431→`adminAPI`) calls `telemetry.Service.FunnelMetrics(...)`, which is
  1432→where the actual MongoDB queries live. `ADMIN_SERVICE_FUNCS` is a
  1433→curated set of these service-method names (FunnelMetrics,
  1434→CustomEventSummary, EngagementMetrics, RetentionCohorts, KPIs,
  1435→ListEventTypes, countDistinct, weeklyActiveUsers, monthlyActiveUsers,
  1436→topCustomEvents, creditConsumptionTrend, medianTimeToFirstPurchase,
  1437→subscriberTrend, mrrTrend, GetAggregateMetrics, GetCurrentMetrics,
  1438→GetIntegrationCounts24h, AdminGetMetrics, AdminListTransactions,
  1439→GetOrCreatePrice, resolveStripeProducts, buildProductNameMap, Load,
  1440→Reload, Set, Seed). Functions in this set are treated as admin-scoped.
  1441→
  1442→#### 4. New Query dataclass fields
  1443→
  1444→Each `Query` now records:
  1445→
  1446→- `route_scope` — admin | tenant | auth | public | cli | background |
  1447→  testutil | unknown
  1448→- `is_admin_handler`, `is_background_task`, `is_public_endpoint`,
  1449→  `is_auth_flow`, `is_cli_tool` — boolean flags
  1450→- `collection_has_tenant_id` — None if struct not found, True/False
  1451→  otherwise
  1452→- `collection_is_user_scoped` — True if the struct has a `userId` bson
  1453→  field
  1454→- `has_user_id_filter` — True if the filter contains `userId`
  1455→- `suppression_reason` — populated when downgraded from a potential
  1456→  violation to MEDIUM (one of: `test-util`, `cli-tool`,
  1457→  `background-task`, `admin-handler`, `public-endpoint`,
  1458→  `global-by-design`, `user-scoped`, `auth-flow`, `safe-unique-key`,
  1459→  `struct-supports-tenant-id`, `exempt-collection`)
  1460→
  1461→#### 5. Classification priority order
  1462→
  1463→The suppression heuristics are applied in this priority order; the
  1464→first match wins and downgrades the query to MEDIUM informational:
  1465→
  1466→1. `has_tenant_id` → OK
  1467→2. `is_testutil` → MEDIUM (test-util)
  1468→3. `is_cli_file` → MEDIUM (cli-tool)
  1469→4. `is_background_task` → MEDIUM (background-task)
  1470→5. `is_admin_handler` → MEDIUM (admin-handler)
  1471→6. `is_public_endpoint` → MEDIUM (public-endpoint)
  1472→7. `collection_is_global` → MEDIUM (global-by-design)
  1473→8. `coll_is_user_scoped and has_user_id` → OK (user-scoped)
  1474→9. `is_auth_flow and (has_user_id or safe_key)` → MEDIUM (auth-flow)
  1475→10. `safe_key` → MEDIUM (safe-unique-key)
  1476→11. `is_exempt` → MEDIUM (exempt-collection, legacy fallback)
  1477→12. `InsertOne/InsertMany on a struct that declares tenantId` → MEDIUM
  1478→    (struct-supports-tenant-id)
  1479→13. Otherwise: write ops → CRITICAL, read ops → HIGH

  1574→### What the struct flattener does (Tool 1)
  1575→
  1576→1. Loads packages with `packages.Load(cfg, "./...")` using
  1577→   `NeedName | NeedFiles | NeedTypes | NeedTypesInfo | NeedSyntax |
  1578→   NeedDeps | NeedImports | NeedModule`.
  1579→2. For each package, iterates the package scope's `*types.TypeName`
  1580→   objects, keeping only those whose underlying type is `*types.Struct`.
  1581→3. Recursively flattens fields: embedded `*types.Named` / pointer-to-
  1582→   named structs are inlined (drilling through `*types.Pointer` and
  1583→   `*types.Named.Underlying()`). Non-struct embedded fields are emitted
  1584→   as regular fields with `Embedded: true`.
  1585→4. Parses both `json:` and `bson:` struct tags via
  1586→   `reflect.StructTag.Get`, returning the leading name component
  1587→   (before any `,omitempty`). `"-"` is preserved as `-`.
  1588→5. Renders each type as a `StructInfo` with `Name`, `Package`,
  1589→   `File` (relative to the working directory, i.e. the analyzed module
  1590→   root), and `Fields []FieldInfo`. Output is a stable-sorted JSON
  1591→   array written to stdout or `-out FILE`.
  1592→6. Empty structs serialize `fields: []` (not `null`), so Python
  1593→   consumers can `for f in struct["fields"]:` without a NoneType guard.
  1594→
  1595→CLI:
  1596→```
  1597→go run scripts/go/graphify_struct_flattener/main.go [-out FILE] [-v] [-tests] [PATTERN ...]
  1598→```
  1599→
  1600→### What the SSA filter tracer does (Tool 2)
  1601→
  1602→For each function whose SSA contains a call to one of `Find`,
  1603→`FindOne`, `FindOneAndUpdate`, `FindOneAndDelete`, `FindOneAndReplace`,
  1604→`UpdateOne`, `UpdateMany`, `DeleteOne`, `DeleteMany`, `InsertOne`,
  1605→`InsertMany`, `CountDocuments`, `Aggregate`, `ReplaceOne`, `BulkWrite`,
  1606→the tool emits a `FunctionReport` with up to three classes of
  1607→`Finding`:
  1608→
  1609→1. **`literal`** — `bson.M{...}` / `bson.D{...}` / `map[string]interface{}{...}`
  1610→   composite literals (the underlying type of `bson.M`). Detected via
  1611→   AST walk over the function body, with precise type resolution
  1612→   through `packages.TypesInfo.Types[lit]`. Both `*types.Named`
  1613→   (e.g. `bson.E`) and `*types.Alias` (e.g. `bson.M` itself, which is
  1614→   `type M = map[string]any`) are handled. For `bson.M`, keys are the
  1615→   `*ast.BasicLit` STRING keys of each `*ast.KeyValueExpr`. For
  1616→   `bson.D`, keys come from the `Key: "..."` field of each `bson.E`
  1617→   element (both named-field and positional forms). The literal's
  1618→   source range is recorded so the MapUpdate pass can dedupe updates
  1619→   that belong to the literal construction.
  1620→
  1621→2. **`map_update`** — `ssa.MapUpdate` instructions whose `Map.Type()`
  1622→   is `map[string]interface{}` (i.e. `bson.M`). The map type is
  1623→   unwrapped through `*types.Alias.Underlying()` first so that
  1624→   variables explicitly typed as `bson.M` are matched. MapUpdates
  1625→   whose source position falls inside a recorded literal range are
  1626→   skipped — they are the lowered form of a `bson.M{...}` literal,
  1627→   already reported by pass 1. The remaining updates are user-written
  1628→   mutations like `filter["$or"] = [...]`. The key is extracted via
  1629→   `constant.StringVal`; non-const keys are reported as `<dynamic>`.
  1630→
  1631→3. **`struct_type`** — calls to `InsertOne` / `InsertMany` /
  1632→   `ReplaceOne` / `FindOneAndReplace` whose document argument is a
  1633→   struct (or slice of structs). SSA wraps struct values in
  1634→   `*ssa.MakeInterface` (because the parameter type is `interface{}`),
  1635→   so the tool unwraps `MakeInterface.X.Type()` to recover the
  1636→   concrete struct type. Pointer and slice element types are drilled
  1637→   through, and the struct's bson-tagged field names are emitted
  1638→   (recursively flattening embedded structs, same as Tool 1).
  1639→
  1640→CLI:
  1641→```
  1642→go run scripts/go/graphify_filter_tracer/main.go [-out FILE] [-v] [-tests] [PATTERN ...]
  1643→```

  1722→### Implementation notes
  1723→
  1724→- **Toolchain**: `golang.org/x/tools v0.48.0` requires Go ≥ 1.25. The
  1725→  workspace has Go 1.23.4 installed; `GOTOOLCHAIN=auto` (the default)
  1726→  downloads `go1.25.12` on demand into the module cache. The
  1727→  `scripts/go/go.mod` declares `go 1.25.0` so this happens
  1728→  transparently.
  1729→- **Workspace setup**: `go run path/to/main.go` from inside
  1730→  `repos/lastsaas/backend` requires the backend's `go.mod` to provide
  1731→  `x/tools` — which it doesn't. Two solutions are supported:
  1732→    1. **`go.work` at `/home/z/my-project/`** (committed) includes
  1733→       both `scripts/go` and `repos/lastsaas/backend`, so `go run`
  1734→       from anywhere under the project root resolves `x/tools`
  1735→       automatically. The backend's own `go build ./...` is
  1736→       unaffected.
  1737→    2. **Pre-built binaries**: `go build -o /tmp/graphify-struct-flattener
  1738→       ./graphify_struct_flattener/` produces a standalone binary that
  1739→       can be invoked from any directory with no Go-side setup.
  1740→       Verified working.
  1741→- **`*types.Alias` handling**: Go 1.22+ represents type aliases
  1742→  (`type M = map[string]any`) as `*types.Alias`, not `*types.Named`.
  1743→  Both tools unwrap `*types.Alias.Underlying()` before doing type
  1744→  discrimination, so `bson.M` is correctly classified as a
  1745→  `map[string]interface{}` literal / map-update target. Without this,
  1746→  zero `bson.M` literals would be detected.
  1747→- **`*ssa.MakeInterface` unwrapping**: `InsertOne(ctx, document
  1748→  interface{})` boxes the struct argument in a `*ssa.MakeInterface`.
  1749→  The tracer recovers the concrete struct type via
  1750→  `MakeInterface.X.Type()` before extracting bson field names.
  1751→- **Position-based deduplication**: SSA lowers `bson.M{"foo": bar}`
  1752→  into `MakeMap` + `MapUpdate`. To avoid reporting these MapUpdates
  1753→  twice (once as part of the literal, once as a "mutation"), the
  1754→  tracer records the source byte-range of every detected composite
  1755→  literal and skips MapUpdates whose position falls inside any
  1756→  recorded range. Only explicit `filter["x"] = y` statements outside
  1757→  any literal range survive as `map_update` findings.
  1758→- **Stable output**: Both tools sort their output by
  1759→  `(package, file, line)` so re-running on the same input produces
  1760→  byte-identical JSON, which makes diffing in CI tractable.
  1761→- **Empty slices**: All `[]T` fields in the JSON schema initialize as
  1762→  `[]T{}` (not `nil`), so the JSON serializes as `[]` rather than
  1763→  `null`. Python consumers can iterate without `or []` guards.

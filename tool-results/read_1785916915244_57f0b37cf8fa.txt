    26→    26→### What the interface analyzer does
    27→    27→

    30→    30→2. Parses every `type X interface { ... }` declaration — including embedded
    31→    31→   interfaces (same-package embeddings are flattened) and multi-line method
    32→    32→   signatures.
    33→    33→3. Parses every `type Y struct { ... }` declaration and every method bound
    34→    34→   to it (both value receivers `func (s Y) M()` and pointer receivers
    35→    35→   `func (s *Y) M()`).
    36→    36→4. For each interface, checks every struct's method set and decides whether
    37→    37→   the struct (value form `T` or pointer form `*T`) satisfies the interface.

    39→    39→   - All interfaces with method count, file, and package
    40→    40→   - Which structs implement each interface, with value vs pointer receiver
    41→    41→   - Interfaces with 0 implementors (dead) — flagged for removal

    52→    52→### What the middleware analyzer does
    53→    53→
    54→    54→1. Walks every `.go` file and detects middleware usage patterns:
    55→    55→   - `router.Use(...)` / `api.Use(...)` / `r.Use(...)` — gorilla/mux style
    56→    56→   - `middleware.Func(...)` factory calls (e.g. `middleware.RequireRole(role)`)
    57→    57→   - Method-style middleware: `authMiddleware.RequireAuth`, `metricsCollector.Middleware(...)`
    58→    58→   - Manual nesting: `handler := m1(m2(m3(finalHandler)))`
    59→    59→   - `http.Handler` wrapping (`c.Handler(...)`, `http.HandlerFunc(...)`)
    60→    60→   - `rateLimiter.RateLimitHandler(config, keyFunc, handler)` — per-route
    61→    61→     rate-limit pattern
    62→    62→2. Reconstructs execution order: outermost wrapper runs first; innermost is
    63→    63→   the terminal handler.
    64→    64→3. For each middleware definition, inspects the function body and decides:
    65→    65→   - **runs_before** — does work before calling `next.ServeHTTP`
    66→    66→   - **runs_after** — does work after `next.ServeHTTP` (or via `defer`)
    67→    67→   - **short_circuits** — may return without calling `next.ServeHTTP`
    68→    68→     (proactive request rejection). Detection uses `http.Error(...)` /
    69→    69→     `WriteHeader(http.StatusXXX)` calls that are NOT inside a `defer`
    70→    70→     block, so panic-recovery middleware like `Recovery` is correctly
    71→    71→     classified as *not* short-circuiting.
    72→    72→4. Emits a visual chain for every router, e.g.:
    73→    73→   ```
    74→    74→   Request → Recovery → BodySizeLimit → SecurityHeaders → CORS → Metrics → Router (Handler) → Response
    75→    75→   ```
    76→    76→   with ✋ markers on short-circuiting middleware.
    77→    77→5. Per-router stacks (combining multiple `.Use(...)` calls on the same
    78→    78→   router in declaration order).
    79→    79→6. Rate-limit site inventory — every endpoint wrapped with
    80→    80→   `RateLimitHandler` is listed.
    81→    81→7. Emits both Markdown (`MIDDLEWARE.md`) and JSON (`middleware.json`).
    82→    82→
    83→    83→CLI:
    84→    84→```
    85→    85→python scripts/graphify_middleware.py [path] [--out report.md] [--json]
    86→    86→                                       [--include-tests]
    87→    87→```

   170→   170→## Task ID: backend-4 — Go error handling audit
   171→   171→
   172→   172→**Date**: 2026-08-05
   173→   173→**Scope**: Build a Python analyzer that audits Go source code for error
   174→   174→handling patterns and persist its reports to `/home/z/my-project/public/`.
   175→   175→
   176→   176→### Files created
   177→   177→
   178→   178→- `scripts/graphify_errors.py` — Go error handling pattern auditor
   179→   179→
   180→   180→### Outputs written to `public/`
   181→   181→
   182→   182→- `error-audit.json` (≈ 320 KB) — full machine-readable audit report
   183→   183→- `ERROR_AUDIT.md` (≈ 230 KB) — human-readable audit summary
   184→   184→
   185→   185→### What the analyzer does
   186→   186→
   187→   187→1. Walks every `.go` file (excluding `vendor/`, `node_modules/`, `.git/`,
   188→   188→   `graphify-out/`, `testdata/`) under the target path. Single-file and
   189→   189→   directory paths are both supported.
   190→   190→2. For each file, masks out string literals and comments (preserving
   191→   191→   length and newlines) so brace/paren matching is robust against
   192→   192→   braces appearing inside strings or comments.
   193→   193→3. Locates every named top-level function and method declaration via
   194→   194→   regex + brace matching, building per-function `(start_line, end_line)`
   195→   195→   ranges so each finding can be attributed to its containing function.
   196→   196→4. Detects four classes of error-handling constructs:
   197→   197→   - **`if X != nil { ... }` blocks** — located via `IF_NIL_RE`, body
   198→   198→     extracted via brace matching, then classified into one of:
   199→   199→       - `proper_handling` (LOW) — body returns `err` (directly or via
   200→   200→         `fmt.Errorf("...: %w", err)` / `errors.Wrap(err, ...)`), OR
   201→   201→         terminates with `os.Exit(non-zero)` / `log.Fatal*` / `t.Fatal*`
   202→   202→         after reporting the error.
   203→   203→       - `panic_on_error` (MEDIUM) — body calls `panic(...)`.
   204→   204→       - `logged_only` (MEDIUM) — body has no `return`, but reports the
   205→   205→         error via `log.*` / `slog.*` / `fmt.Print*` / `respondWithError`
   206→   206→         / `http.Error` / `t.Error*` (i.e. error is acknowledged but not
   207→   207→         propagated).
   208→   208→       - `swallowed` (HIGH) — empty body, or body that returns without
   209→   209→         `err` (dropping the error info), or body that does anything else
   210→   210→         without propagating/reporting.
   211→   211→   - **Ignored errors** — `result, _ := someFunc(...)` patterns where the
   212→   212→     last return value is discarded with `_`. `for k, _ := range m` is
   213→   213→     excluded (map iteration idiom).
   214→   214→   - **Missing error checks** — statement-form method calls (not
   215→   215→     assigned, not preceded by `defer`/`go`) to a known error-returning
   216→   216→     method such as `Close`, `Write`, `Read`, `InsertOne`, `UpdateOne`,
   217→   217→     `DeleteOne`, `BulkWrite`, `Marshal`, `Unmarshal`, `Encode`, `Decode`,
   218→   218→     `Parse`, `Exec`, `Commit`, `Ping`, etc. The **outermost** call in a
   219→   219→     chain is examined (e.g. `collection.FindOne(...).Decode(&x)` is
   220→   220→     attributed to `Decode`, not `FindOne`). Free-function calls (no `.`
   221→   221→     receiver) are skipped to avoid noise from custom helpers.
   222→   222→   - **Panic on error** — flagged separately so non-`init()` panics can
   223→   223→     be reviewed (per the spec, panicking is acceptable in `init()` but
   224→   224→     risky elsewhere).
   225→   225→5. Skips lines inside `if X != nil { ... }` blocks for the missing-check
   226→   226→   scan so the same error site isn't double-counted.
   227→   227→6. For each finding, records: file (relative to project root), line,
   228→   228→   end_line, containing function, pattern type, severity, code snippet
   229→   229→   (capped at 6 lines), and a note explaining the heuristic that fired.
   230→   230→7. Test files (`*_test.go`) are scanned separately; only their aggregate
   231→   231→   statistics appear in the report (test-file findings are not included
   232→   232→   in the detailed findings list, per the spec).
   233→   233→
   234→   234→### CLI
   235→   235→
   236→   236→```
   237→   237→python graphify_errors.py [path] [--out report.md] [--json] [--include-tests]
   238→   238→```
   239→   239→
   240→   240→- `path` — file or directory to audit (default: `.`).
   241→   241→- `--out report.md` — write markdown report to this path in addition to

   243→   243→- `--json` — print the JSON report to stdout.

   300→   300→### Implementation notes
   301→   301→
   302→   302→- The script is pure-Python (no `tree-sitter` dependency, unlike
   303→   303→  `graphify_verify.py`); it relies on a custom string/comment masker
   304→   304→  plus brace matching, which is sufficient for Go's relatively regular
   305→   305→  syntax.
   306→   306→- The `extract_outermost_method` helper walks a single source line,
   307→   307→  tracks `()` / `[]` / `{}` depth, and returns the **last** top-level
   308→   308→  call's method name — this correctly handles chained calls like
   309→   309→  `client.Database("x").Collection("y").InsertOne(ctx, doc)` by
   310→   310→  attributing the call to `InsertOne` (the actual error-returning call),
   311→   311→  not `Database` or `Collection` (which return builder types).
   312→   312→- Free-function calls are skipped from the missing-check scan because
   313→   313→  the auditor cannot infer their signatures without type information.
   314→   314→  This avoids false positives like `apierror.Write(w, status, ...)` —
   315→   315→  a void package-level helper that happens to share a name with
   316→   316→  `io.Writer.Write`.
   317→   317→- `WriteString` is deliberately **not** in the error-returning set:
   318→   318→  `strings.Builder.WriteString` and `bytes.Buffer.WriteString` always
   319→   319→  return a nil error, and including it produced 64 false positives in
   320→   320→  `internal/api/handlers/docs.go` alone (the OpenAPI HTML generator
   321→   321→  uses `sb.WriteString(...)` extensively).
   322→   322→- The classifier recognizes several legitimate "non-propagating but
   323→   323→  acceptable" patterns and treats them as `proper_handling`:
   324→   324→  - `os.Exit(non-zero)` after printing the error (CLI termination).
   325→   325→  - `log.Fatal*` (calls `os.Exit(1)` internally).
   326→   326→  - `t.Fatal*` (test termination — fails the test immediately).
   327→   327→  - `return fmt.Errorf("...: %w", err)` / `errors.Wrap(err, ...)`
   328→   328→    (error wrapping).
   329→   329→  Returning a *new* error without the original (e.g.
   330→   330→  `return errors.New("oops")`) is classified as `swallowed` because
   331→   331→  the original error info is dropped.
   332→   332→- The HTTP-handler pattern
   333→   333→  `if err != nil { respondWithError(w, status, msg); return }` is
   334→   334→  classified as `logged_only` (MEDIUM) rather than `swallowed` (HIGH)
   335→   335→  because the error IS acknowledged (it triggers the error response)
   336→   336→  even though the original `err` value isn't propagated. The
   337→   337→  `ERROR_REPORT_RE` regex covers `respondWithError`, `http.Error`,
   338→   338→  `writeError`, `sendError`, `c.JSON`, and similar response helpers.

   363→   363→## Task ID: fix-auditor — Eliminate swallowed-error false positives
   364→   364→
   365→   365→**Date**: 2026-08-05
   366→   366→**Scope**: Refactor `scripts/graphify_errors.py` so the "swallowed" classifier
   367→   367→recognises the legitimate Go error-handling patterns the `lastsaas` backend
   368→   368→uses, then re-run the audit and refresh the public reports.
   369→   369→
   370→   370→### Problem
   371→   371→
   372→   372→The previous auditor reported **140 "swallowed" errors** in the `lastsaas`
   373→   373→backend, but only ~6 of those were genuinely broken. The remaining ~134
   374→   374→were valid Go patterns the classifier didn't recognise as "handled":
   375→   375→
   376→   376→- `if err != nil { slog.Warn(...); return }` — error logged then early-return
   377→   377→- `if err != nil { http.Redirect(...); return }` — OAuth callback redirects
   378→   378→  the browser to a login-error URL
   379→   379→- `if err != nil { respondWithError(w, ...); return }` — HTTP handler
   380→   380→  reports the error to the client and short-circuits
   381→   381→- `if err != nil { page = 1 }` — input clamping (parse-error → default)
   382→   382→- `if err != nil { delivery.Success = false; ... }` — failure flagging on
   383→   383→  a struct field
   384→   384→- `if err != nil { if err == mongo.ErrNoDocuments { ... } }` — sentinel
   385→   385→  error type check (expected "not found" branch)
   386→   386→- `if err != nil { slog.Warn(...); continue }` — batch-processing skip
   387→   387→- `if err != nil { fmt.Fprintf(os.Stderr, ...); return }` — CLI tool logs
   388→   388→  the error to stderr and exits the function

   411→   411→# `swallowed` as `logged_only` (MEDIUM). `fmt.Errorf` is intentionally
   412→   412→# excluded — it constructs a new error rather than logging one.
   413→   413→SLOG_LOG_RE  = r'\bslog\.(?:Warn|Error|Info|Debug)(?:ln|f)?\s*\('
   414→   414→LOG_PRINT_RE = r'\blog\.(?:Print|Printf|Println|Fatal*|Panic*)\s*\('
   415→   415→FMT_PRINT_RE = r'\bfmt\.(?:Print*|Fprint*|Sprint*)\s*\('     # excludes Errorf

   419→   419→# when the original `err` is not propagated.
   420→   420→HTTP_REDIRECT_RE = r'\bhttp\.Redirect\s*\('

   427→   427→#### `RETURN_ERR_RE` made case-insensitive
   428→   428→
   429→   429→The original `r'\breturn\b[^;]*\berr\b'` only matched lowercase `err`, so
   430→   430→`return fmt.Errorf("...: %w", res.Err())` (which wraps the error properly
   431→   431→via `%w`) was being misclassified as `swallowed` by the
   432→   432→`RETURN_NEW_ERR_RE` fallback. Adding `re.IGNORECASE` lets it match `Err`
   433→   433→too while still requiring `err` to be a complete word (so `ferrisWheel`
   434→   434→isn't matched).

   436→   436→#### `classify_err_body` refactor
   437→   437→
   438→   438→The new classification order (each step short-circuits):
   439→   439→
   440→   440→1.  Empty body                                    → `swallowed`
   441→   441→2.  `panic(...)`                                  → `panic_on_error`
   442→   442→3.  Terminal exit (`os.Exit(non-zero)`, `log.Fatal*`, `t.Fatal*`) → `proper_handling`
   443→   443→4.  `return ...err...` (case-insensitive)         → `proper_handling`
   444→   444→5.  **Proper-handler patterns** (any of):
   445→   445→    - `http.Redirect(...)`
   446→   446→    - `respondWithError(...)` / `http.Error(...)` / `writeError(...)` / etc.
   447→   447→    - `mongo.ErrNoDocuments` / `ErrNoDocuments` check
   448→   448→    - `continue` statement (batch processing)
   449→   449→    - Assignment to a variable or struct field
   450→   450→      (`page = 1`, `delivery.Success = false`, …)  → `proper_handling`
   451→   451→6.  **Logging patterns** (any of):
   452→   452→    - `slog.Warn/Error/Info/Debug(...)`
   453→   453→    - `log.Print*`/`Fatal*`/`Panic*(...)`
   454→   454→    - `fmt.Print*`/`Fprint*`/`Sprint*(...)`
   455→   455→      (excludes `fmt.Errorf` — that's error construction)
   456→   456→    - `fmt.Fprint*(os.Stderr, ...)`               → `logged_only`
   457→   457→7.  `return` (bare or new error like
   458→   458→    `return errors.New("oops")`)                  → `swallowed`
   459→   459→8.  `t.Error*` (no return, no other handler)      → `logged_only`
   460→   460→9.  Body consists ONLY of logging calls
   461→   461→    (fallback `LOG_CALL_RE` sweep)                → `logged_only`
   462→   462→10. Anything else                                 → `swallowed`
   463→   463→
   464→   464→The key change is that steps 5 and 6 are checked BEFORE the `has_return`
   465→   465→branch. This is what eliminates the bulk of the false positives: bodies
   466→   466→like `slog.Warn(...); return` and `http.Redirect(...); return` are now
   467→   467→recognised as acknowledged/handled rather than swallowed.
   468→   468→
   469→   469→**Important behavioural change**: `respondWithError(...)` / `http.Error(...)`
   470→   470→were previously classified as `logged_only` (MEDIUM); they are now
   471→   471→`proper_handling` (LOW) per the spec — the error IS reported to the
   472→   472→client and the request IS short-circuited, which is a legitimate
   473→   473→production handling pattern for HTTP handlers.

   600→   600→### What the N+1 analyzer does
   601→   601→
   602→   602→1. Walks every `.go` file (excluding `*_test.go` by default) under the
   603→   603→   target path, masks out string literals and comments (preserving length
   604→   604→   and newlines), then locates every loop header
   605→   605→   (`for ... range ...`, `for init; cond; post { ... }`,
   606→   606→   `for cond { ... }`, `for { ... }`) and finds the matching `}` via
   607→   607→   depth-counting brace matching.
   608→   608→2. For each loop body (lines `start_line+1` to `end_line`), scans every
   609→   609→   line for a MongoDB collection method call —
   610→   610→   `Find`, `FindOne`, `InsertOne`, `InsertMany`, `UpdateOne`,
   611→   611→   `UpdateMany`, `ReplaceOne`, `DeleteOne`, `DeleteMany`, `Aggregate`,
   612→   612→   `CountDocuments`, `EstimatedDocumentCount`. Option-builder calls
   613→   613→   (`options.Find()`, `options.FindOne()`) are skipped.
   614→   614→3. For each DB-op line inside a loop body, resolves the collection via
   615→   615→   three strategies: literal `db.Collection("name")`, accessor call
   616→   616→   `m.Users()` (resolved via the codebase's accessor map), or aliased
   617→   617→   local variable `col := m.Users()`. Also recognises dynamic collection
   618→   618→   names (`db.Collection(name)` where `name` is a variable) and labels
   619→   619→   them `dynamic:<varname>`.
   620→   620→4. Records for each finding: file, loop start line, loop close line,
   621→   621→   call line (where the DB op actually appears), containing function,
   622→   622→   loop kind (`range` / `three-form` / `condition` / `infinite`),
   623→   623→   loop variable, MongoDB operation, collection, code snippet, a
   624→   624→   context-specific remediation suggestion (different for reads vs
   625→   625→   writes vs deletes), and a risk classification.
   626→   626→5. **Risk**: HIGH for queries in user-facing handler code; MEDIUM for
   627→   627→   admin/CLI/batch paths (still bad, but lower blast radius).
   628→   628→6. Emits both Markdown (`N_PLUS_1.md`) and JSON (`n-plus-1.json`).
   629→   629→
   630→   630→### What the missing-index analyzer does
   631→   631→
   632→   632→1. **Index inventory.** Walks every `.go` file and parses every
   633→   633→   `mongo.IndexModel{ Keys: bson.D{...}, Options: ... }` declaration.
   634→   634→   Two patterns are recognised:
   635→   635→
   636→   636→   - The slice-of-anonymous-struct form used by
   637→   637→     `internal/db/mongodb.go::ensureIndexes()`:
   638→   638→
   639→   639→       ```go
   640→   640→       indexes := []struct {
   641→   641→           collection string
   642→   642→           models     []mongo.IndexModel
   643→   643→       }{
   644→   644→           {
   645→   645→               "users",
   646→   646→               []mongo.IndexModel{
   647→   647→                   {Keys: bson.D{{Key: "email", Value: 1}}, Options: ...},
   648→   648→                   ...
   649→   649→               },
   650→   650→           },
   651→   651→           ...
   652→   652→       }
   653→   653→       ```
   654→   654→
   655→   655→     The collection comes from the string literal that precedes each
   656→   656→     `[]mongo.IndexModel{` block. Individual entries are extracted by
   657→   657→     iterating top-level `{...}` blocks (brace matching, not regex) and
   658→   658→     splitting each entry on the first top-level `,` to separate `Keys:`
   659→   659→     from `Options:`. This correctly handles the nested braces in
   660→   660→     `bson.D{{Key: "f", Value: 1}}` and the chained `SetUnique(true).SetSparse(true)`
   661→   661→     options.
   662→   662→
   663→   663→   - The standalone `mongo.IndexModel{...}` form used by
   664→   664→     `internal/middleware/ratelimit.go`:
   665→   665→
   666→   666→       ```go
   667→   667→       coll.Indexes().CreateOne(ctx, mongo.IndexModel{
   668→   668→           Keys:    bson.D{{Key: "expiresAt", Value: 1}},
   669→   669→           Options: options.Index().SetExpireAfterSeconds(0),
   670→   670→       })
   671→   671→       ```
   672→   672→
   673→   673→     The collection is resolved by binary-searching backwards for the
   674→   674→     nearest preceding collection-binding site (`db.Collection("name")`
   675→   675→     literal, alias variable, or a `Collection("name").Indexes()` call
   676→   676→     on the same expression).
   677→   677→
   678→   678→2. **Query scan.** Walks every `.go` file and locates each MongoDB
   679→   679→   collection method call. The first-argument filter is parsed from the
   680→   680→   `bson.M{}` / `bson.D{}` literal, with a multi-line look-ahead window
   681→   681→   so multi-line filter literals are captured. InsertOne/InsertMany/
   682→   682→   Aggregate are skipped (no filter to check).
   683→   683→3. **Coverage check.** For each query the filter fields are compared
   684→   684→   against the collection's index inventory. A query is covered if ANY
   685→   685→   of: it filters by `_id` (always indexed by MongoDB), it filters by a
   686→   686→   single-field index, or it filters by the leading field of a compound
   687→   687→   index. Queries with no covering index are flagged as `no_index`.
   688→   688→4. **Spec-required check.** Each query is also checked against a small
   689→   689→   SaaS-domain rule set (`REQUIRED_INDEX_FIELDS`): `email` on `users`,
   690→   690→   `slug` on `tenants`, `token` on `invitations` / `verification_tokens`
   691→   691→   / `auth_codes`, `tenantId` on multi-tenant collections, `userId` on
   692→   692→   membership/log/token collections, etc. Queries that filter on a
   693→   693→   spec-required field that isn't indexed are flagged as `missing_required`.
   694→   694→5. **Multi-tenant hygiene.** Empty-filter queries on multi-tenant
   695→   695→   collections (`tenant_memberships`, `audit_log`, `system_logs`,
   696→   696→   `telemetry_events`, `usage_events`, `financial_transactions`,
   697→   697→   `messages`, `api_keys`, `webhooks`, `webhook_deliveries`,
   698→   698→   `sso_connections`, `announcements`) are flagged as
   699→   699→   `multi_tenant_unfiltered` — full collection scans that risk
   700→   700→   cross-tenant data leaks.
   701→   701→6. **Risk**: HIGH for queries on large collections (logs, events,
   702→   702→   telemetry, audit, deliveries, metrics) without a covering index, and
   703→   703→   for queries on spec-required fields without an index. MEDIUM for
   704→   704→   small/static-data collections without coverage and for multi-tenant
   705→   705→   empty-filter queries on small collections.
   706→   706→7. Emits both Markdown (`MISSING_INDEXES.md`) and JSON
   707→   707→   (`missing-indexes.json`). The report includes a full **index
   708→   708→   inventory** table showing every declared index, its fields, leading
   709→   709→   field, and unique/TTL/sparse flags.
   710→   710→
   711→   711→### What the dead-code analyzer does
   712→   712→
   713→   713→1. Walks every non-test `.go` file under the target path, parses every
   714→   714→   `func [recv] Name(...)` declaration (free functions and methods), and
   715→   715→   finds the body's line range via brace matching.
   716→   716→2. **Exclusions** (functions never reported as dead):
   717→   717→   - `main()` and `init()` — Go entry points.
   718→   718→   - `Test*`, `Benchmark*`, `Fuzz*`, `Example*` — testing framework
   719→   719→     entry points.
   720→   720→   - Well-known interface-satisfying methods that may be invoked via
   721→   721→     interface dispatch or reflection: `String`, `Error`, `Unwrap`,
   722→   722→     `Is`, `As`, `MarshalJSON`, `UnmarshalJSON`, `MarshalText`,
   723→   723→     `Read`/`Write`/`Close`/`Flush`, `Len`/`Less`/`Swap`,
   724→   724→     `ServeHTTP`, `Value`/`Scan`, `Format`, `Deadline`/`Done`/`Err`,
   725→   725→     etc.
   726→   726→   - Stub functions whose body is just `panic("not implemented")` /
   727→   727→     `panic("TODO")` / `panic("unreachable")`.
   728→   728→3. For every remaining function, the codebase is searched for
   729→   729→   whole-word references to the function name across ALL `.go` files
   730→   730→   (including `*_test.go` — tests are legitimate external callers).
   731→   731→   String literals and comments are masked out before searching so
   732→   732→   doc-comment mentions don't count as references.
   733→   733→4. **Unexported function**: reported as dead if it has zero references
   734→   734→   anywhere outside its own definition line.
   735→   735→5. **Exported function**: reported as dead if no OTHER file references
   736→   736→   it. Same-file references don't count because removing the function
   737→   737→   would also remove those callers — they're part of the same dead
   738→   738→   subtree.
   739→   739→6. Each finding records: function name, file, line, end_line,
   740→   740→   function_kind (`exported` / `unexported`), receiver type (for
   741→   741→   methods), `external_refs` (number of other files referencing it),
   742→   742→   `same_file_refs` (number of references in same file outside the
   743→   743→   definition), `total_refs`, code snippet (from raw source, not
   744→   744→   masked), severity (always LOW), and a note.
   745→   745→7. Emits both Markdown (`DEAD_CODE_GO.md`) and JSON (`dead-code-go.json`).

   886→   886→### Implementation notes
   887→   887→
   888→   888→- All three scripts share the same string/comment masker (preserves
   889→   889→  length and newlines so brace-matching is robust) and the same
   890→   890→  function-body finder (regex for the header + brace matching for the
   891→   891→  body). They diverge in what they look for inside the bodies.
   892→   892→- The N+1 analyzer reuses the collection-resolution strategy from
   893→   893→  `graphify_db_queries.py` (literal / accessor / alias, in that order)
   894→   894→  but adds a fourth case: dynamic collection names from
   895→   895→  `db.Collection(<var>)` are labelled `dynamic:<varname>` so the report
   896→   896→  is informative rather than just `<unknown>`.
   897→   897→- The missing-index analyzer's index parser was tricky because
   898→   898→  `ensureIndexes()` uses a slice of anonymous structs with a
   899→   899→  `[]mongo.IndexModel{...}` slice field per collection. The first
   900→   900→  attempt (regex-only) failed because the nested braces in
   901→   901→  `bson.D{{Key: "f", Value: 1}}` confuse any regex that tries to match
   902→   902→  a single entry's `{...}` block. The fix is a two-stage parse: regex
   903→   903→  to find each `"<coll>", []mongo.IndexModel{...}` block, then a small
   904→   904→  brace-matching iterator (`_iter_top_level_entries`) to walk each
   905→   905→  `{Keys: ..., Options: ...}` entry inside, then a depth-aware
   906→   906→  splitter (`_extract_keys_and_options`) to separate the two halves on
   907→   907→  the first top-level `,`. This correctly handles compound indexes
   908→   908→  (`bson.D{{Key: "tenantId", Value: 1}, {Key: "createdAt", Value: -1}}`)
   909→   909→  and the chained options (`SetUnique(true).SetSparse(true)`).
   910→   910→- The missing-index analyzer's coverage check has a subtle correctness
   911→   911→  rule: a query is covered if ANY filter field is the leading field of
   912→   912→  any index (single-field or compound). MongoDB can use a compound
   913→   913→  index for a query that filters only on its leading field, but NOT
   914→   914→  for a query that filters only on a trailing field. The script also
   915→   915→  treats `_id` as an implicit single-field index (MongoDB always
   916→   916→  creates it), so any query that filters by `_id` (alone or with other
   917→   917→  fields) is automatically covered — this eliminated ~120 false
   918→   918→  positives on `UpdateOne(filter={"_id": ..., "field": ...})` patterns
   919→   919→  that update a single document by ID.
   920→   920→- The dead-code analyzer keeps two source representations per file:
   921→   921→  masked (for reference search — so identifiers in strings/comments
   922→   922→  don't count) and raw (for snippet rendering). Snippets originally
   923→   923→  came out garbled because they were being sliced from the masked
   924→   924→  text; switched to raw and the snippets now show real source.
   925→   925→- The dead-code analyzer conservatively excludes well-known
   926→   926→  interface-satisfying methods (`String`, `Error`, `MarshalJSON`,
   927→   927→  `ServeHTTP`, `Len`/`Less`/`Swap`, etc.) because they may be called
   928→   928→  via interface dispatch or reflection, which a name-based grep can't
   929→   929→  detect. This trades a few false negatives (some genuinely dead
   930→   930→  `String()` methods exist) for zero false positives — matching the
   931→   931→  spec's "NO false positives" requirement.

   978→   978→### Files created
   979→   979→
   980→   980→- `scripts/graphify_tenant_audit.py` — tenant-isolation security auditor
   981→   981→
   982→   982→### Outputs written to `public/`
   983→   983→
   984→   984→- `tenant-audit.json` (≈ 430 KB) — full machine-readable audit report
   985→   985→- `TENANT_AUDIT.md` (≈ 240 KB) — human-readable audit summary
   986→   986→
   987→   987→### What the auditor does
   988→   988→
   989→   989→1. Walks every `.go` file (excluding `*_test.go` by default,
   990→   990→   `vendor/`, `.git/`, `graphify-out/`) under the target path.
   991→   991→2. Builds an **accessor map** (`{Users: "users", Plans: "plans", ...}`)
   992→   992→   by scanning every `func (recv) Name() *mongo.Collection { return
   993→   993→   <expr>.Collection("name") }` declaration. The `lastsaas` backend
   994→   994→   exposes 38 collection accessors on `*db.MongoDB` (in
   995→   995→   `internal/db/mongodb.go`).
   996→   996→3. Builds a **struct-field index** (`{Invitation: {_id, tenantId, email,
   997→   997→   role, ...}, ...}`) by walking every `type X struct { ... }`
   998→   998→   declaration and extracting the bson field tags. Used to verify
   999→   999→   whether an `InsertOne(ctx, structValue)` carries a `tenantId` field.
  1000→  1000→4. Masks string literals, raw strings, rune literals, line comments,
  1001→  1001→   and block comments (preserving length and newlines) so brace/paren
  1002→  1002→   matching is robust against braces appearing inside strings — while
  1003→  1003→   still slicing argument text from the **raw** source so the bson
  1004→  1004→   string keys (`"tenantId"`, `"_id"`, ...) are visible to the
  1005→  1005→   field-extraction regexes.
  1006→  1006→5. For each MongoDB operation call (`Find`, `FindOne`, `InsertOne`,
  1007→  1007→   `InsertMany`, `UpdateOne`, `UpdateMany`, `DeleteOne`, `DeleteMany`,
  1008→  1008→   `Aggregate`, `CountDocuments`, `EstimatedDocumentCount`,
  1009→  1009→   `FindOneAndUpdate`, `FindOneAndDelete`, `FindOneAndReplace`,
  1010→  1010→   `ReplaceOne`, `UpdateByID`, `BulkWrite`):
  1011→  1011→   - Resolves the underlying collection via literal
  1012→  1012→     `db.Collection("name")`, accessor call `h.db.Users()`, or aliased
  1013→  1013→     variable `col.Find(...)` (traced back to its assignment).
  1014→  1014→   - Extracts the **filter argument** (the 2nd positional argument,
  1015→  1015→     except for `InsertOne`/`InsertMany` where it's the document, for
  1016→  1016→     `Aggregate` where it's the pipeline, for `UpdateByID` where it's
  1017→  1017→     the `_id`, and for `EstimatedDocumentCount` where there is none).
  1018→  1018→   - For **inline `bson.M{}`/`bson.D{}`/`map[string]interface{}{}`**
  1019→  1019→     literals, extracts the field names directly via regex.
  1020→  1020→   - For **variable filters** (`filter := bson.M{...}` followed by
  1021→  1021→     `h.db.X().Find(ctx, filter)`), traces the variable back to its
  1022→  1022→     definition and captures all fields — including **dynamic field
  1023→  1023→     additions** like `filter["tenantId"] = tenant.ID` that appear on
  1024→  1024→     later lines (often inside `if` blocks).
  1025→  1025→   - For **inline struct values** (`models.Invitation{...}`) and
  1026→  1026→     **struct-typed variables** (`invitation := models.Invitation{...}`
  1027→  1027→     followed by `InsertOne(ctx, invitation)`), looks up the struct's
  1028→  1028→     bson field tags and reports whether `tenantId` is declared.
  1029→  1029→   - For **aggregate pipelines** (`pipeline := []bson.M{...}` /
  1030→  1030→     `mongo.Pipeline{...}` / `bson.A{...}`), inspects every `$match`
  1031→  1031→     stage and extracts the filter fields (so `{"$match": bson.M{
  1032→  1032→     "tenantId": tenant.ID, ... }}` correctly counts as
  1033→  1033→     `has_tenant_id = True`).
  1034→  1034→6. Classifies each query as **OK** / **MEDIUM** / **HIGH** / **CRITICAL**:
  1035→  1035→   - **OK** — filter contains `tenantId` or `tenant_id`.
  1036→  1036→   - **MEDIUM** — collection is in the exempt (global) list:
  1037→  1037→     `tenants`, `plans`, `system_config`, `system_logs`, `users`.
  1038→  1038→     Tenant filtering is not strictly required, but the query is still
  1039→  1039→     listed for review.
  1040→  1040→   - **HIGH** — read operation (`Find`, `FindOne`, `Aggregate`,
  1041→  1041→     `CountDocuments`, `EstimatedDocumentCount`) on a tenant-scoped
  1042→  1042→     collection without `tenantId` in the filter.
  1043→  1043→   - **CRITICAL** — write operation (`InsertOne`, `InsertMany`,
  1044→  1044→     `UpdateOne`, `UpdateMany`, `DeleteOne`, `DeleteMany`,
  1045→  1045→     `FindOneAndUpdate`, `FindOneAndDelete`, `FindOneAndReplace`,
  1046→  1046→     `ReplaceOne`, `UpdateByID`, `BulkWrite`) on a tenant-scoped
  1047→  1047→     collection without `tenantId` in the filter.
  1048→  1048→7. Records each query with file, line, function, collection, operation,
  1049→  1049→   filter fields, `has_tenant_id`, `filter_source` (inline / variable /
  1050→  1050→   nil / struct / struct-var / inline-pipeline / variable-pipeline /
  1051→  1051→   by-id / no-filter / bulk-write-models), `risk_level`,
  1052→  1052→   `is_violation`, `is_exempt_collection`, `safe_key_filter` (True when
  1053→  1053→   the filter contains a globally-unique key like `_id`, `tokenHash`,
  1054→  1054→   `slug`, `email`, `name`, `invoiceNumber`, ... — these are likely
  1055→  1055→   false positives because the unique key already constrains the query
  1056→  1056→   to a single document, but they are still listed for manual
  1057→  1057→   confirmation), a multi-line `filter_snippet` from the raw source,
  1058→  1058→   and a human-readable `note` explaining the heuristic that fired.
  1059→  1059→8. Emits both Markdown (`TENANT_AUDIT.md`) and JSON (`tenant-audit.json`).

  1160→  1160→### Implementation notes
  1161→  1161→
  1162→  1162→- The auditor is **pure-Python** (no tree-sitter or Go AST dependency),
  1163→  1163→  following the convention established by `graphify_errors.py` and
  1164→  1164→  `graphify_db_queries.py`. It relies on a custom string/comment masker
  1165→  1165→  plus brace matching, which is sufficient for Go's relatively regular
  1166→  1166→  syntax.
  1167→  1167→- **Masking strategy**: the masker replaces string literals (raw,
  1168→  1168→  interpreted, rune) and comments (line, block) with spaces — preserving
  1169→  1169→  length and newlines. Two parallel text representations are maintained:
  1170→  1170→  - `masked` — used for OP_RE matching (so `.Find(` inside a string
  1171→  1171→    literal doesn't false-match) and for brace/paren depth tracking in
  1172→  1172→    `extract_call_args` and `_collect_brace_window` (so braces inside
  1173→  1173→    strings don't prematurely close a block).
  1174→  1174→  - `raw` — used for slicing argument text and extracting filter fields
  1175→  1175→    (so the bson string keys `"tenantId"`, `"_id"`, etc. are visible to
  1176→  1176→    the field-extraction regexes).
  1177→  1177→  The two representations have identical length and newline positions,
  1178→  1178→  so the same character indices work for both.
  1179→  1179→- **Variable filter tracing**: the auditor tracks three kinds of
  1180→  1180→  per-function variable assignments:
  1181→  1181→  - **Collection aliases** (`col := h.db.Users()`) — used to resolve
  1182→  1182→    `col.Find(...)` calls.
  1183→  1183→  - **Filter variables** (`filter := bson.M{...}` + dynamic additions
  1184→  1184→    `filter["tenantId"] = ...`) — used to resolve
  1185→  1185→    `h.db.X().Find(ctx, filter)` calls. The dynamic-addition regex
  1186→  1186→    runs on the RAW line (not masked) because the string key must be
  1187→  1187→    visible.
  1188→  1188→  - **Pipeline variables** (`pipeline := []bson.M{...}` /
  1189→  1189→    `mongo.Pipeline{...}` / `bson.A{...}`) — used to resolve
  1190→  1190→    `h.db.X().Aggregate(ctx, pipeline)` calls. The `$match` stage
  1191→  1191→    extraction uses `find_block_end` to locate the closing brace of
  1192→  1192→    each `bson.M{...}` block within the `$match` stage, then delegates
  1193→  1193→    to `extract_filter_fields_from_text`.
  1194→  1194→  - **Struct-typed variables** (`invitation := models.Invitation{...}`)
  1195→  1195→    — used to resolve `InsertOne(ctx, invitation)` calls. The struct's
  1196→  1196→    bson field tags are looked up in the struct-field index to
  1197→  1197→    determine whether `tenantId` is declared.
  1198→  1198→- **`EstimatedDocumentCount`**: included in `ALL_OPERATIONS` so it's
  1199→  1199→  detected, but classified specially (`filter_source = "no-filter"`)
  1200→  1200→  because it takes no filter argument. On a tenant-scoped collection
  1201→  1201→  it's HIGH risk (leaks the total document count across all tenants);
  1202→  1202→  on a global collection it's MEDIUM. All 3 occurrences in the
  1203→  1203→  codebase are on exempt collections (`users`, `tenants`, `system_logs`).
  1204→  1204→- **`UpdateByID`**: classified as `safe_key_filter = True` because the
  1205→  1205→  2nd argument is the document `_id` (globally unique). The
  1206→  1206→  `filter_fields` list is set to `["_id"]` so the report shows the
  1207→  1207→  filter clearly.
  1208→  1208→- **`BulkWrite`**: flagged with `filter_source = "bulk-write-models"`
  1209→  1209→  and a note explaining that individual WriteModel operations cannot
  1210→  1210→  be analysed statically. No BulkWrite calls were found in the
  1211→  1211→  codebase.
  1212→  1212→- **`InsertMany`**: the 2nd argument is a slice of documents. The
  1213→  1213→  auditor extracts fields from any inline `bson.M{}` literals in the
  1214→  1214→  slice. If the documents are struct values, the struct fields can't
  1215→  1215→  be easily analysed (each slice element would need its own struct
  1216→  1216→  resolution) — flagged with a note. 2 `InsertMany` calls found, both
  1217→  1217→  on `telemetry_events` (which legitimately has no `tenantId`).
  1218→  1218→- The **safe-key heuristic** is conservative: it only includes truly
  1219→  1219→  globally-unique identifiers (`_id`, `slug`, `tokenHash`, `keyHash`,
  1220→  1220→  `code`, `eventId`, `credentialId`, `machineId`, `email`, `name`,
  1221→  1221→  `invoiceNumber`, `familyId`). It does NOT include `userId` (which is
  1222→  1222→  unique per user but a user can belong to multiple tenants) or `key`
  1223→  1223→  (which is a generic name that happens to be unique in
  1224→  1224→  `branding_assets` but might not be in other collections). Reviewers
  1225→  1225→  can dismiss false positives based on context.
  1226→  1226→- The report separates **real violations** (no safe key, need review)
  1227→  1227→  from **safe-key violations** (likely false positives) so reviewers
  1228→  1228→  can triage efficiently. The per-file section at the end lists every
  1229→  1229→  query (including OK and MEDIUM) for completeness.

  1385→  1385→### How the new heuristics are implemented
  1386→  1386→
  1387→  1387→#### 1. Collection→struct resolver
  1388→  1388→
  1389→  1389→`build_collection_struct_map(accessor_map, struct_fields)` walks each
  1390→  1390→collection name returned by an accessor method, derives the candidate
  1391→  1391→Go struct name using a snake_case → PascalCase heuristic with plural
  1392→  1392→handling (`ies` → `y`, trailing `s` stripped), and confirms it exists
  1393→  1393→in the struct-field index. Hardcoded overrides handle acronym
  1394→  1394→capitalisation (`api_keys` → `APIKey`, `oauth_states` → `OAuthState`,
  1395→  1395→`sso_connections` → `SSOConnection`, `webauthn_credentials` →
  1396→  1396→`WebAuthnCredential`, `counters` → `InvoiceCounter`).
  1397→  1397→
  1398→  1398→`build_user_scoped_collections(csm, sf)` returns the set of
  1399→  1399→collections whose struct has a `userId` bson field — for these, a
  1400→  1400→`userId` filter is a valid scope.
  1401→  1401→
  1402→  1402→`build_global_collections(csm, sf)` returns the set of collections
  1403→  1403→whose struct does NOT declare a `tenantId` field — these are GLOBAL BY
  1404→  1404→DESIGN.
  1405→  1405→
  1406→  1406→#### 2. Route classifier (parses main.go)
  1407→  1407→
  1408→  1408→`build_route_classifier(repo_root)` finds `cmd/server/main.go`, walks
  1409→  1409→every `router.HandleFunc("/path", HANDLER).Methods("VERB")` call, and
  1410→  1410→maps the handler function name to a route scope based on the router
  1411→  1411→variable:
  1412→  1412→
  1413→  1413→- `adminAPI`, `adminWrite`, `adminOwner` → admin (91 handlers)
  1414→  1414→- `tenantAPI`, `tenantSettingsRouter`, `inviteRouter`, `removeRouter`,
  1415→  1415→  `ownerRouter`, `usageAPI`, `telemetryAPI`, `billingAPI`,
  1416→  1416→  `billingOwner` → tenant (18 handlers)
  1417→  1417→- `guarded`, `protectedAuth`, `api`, `router` → auth (32 handlers) or
  1418→  1418→  public (12 handlers — split via the `PUBLIC_ENDPOINT_FUNCS` set)
  1419→  1419→
  1420→  1420→The regex uses the RAW source text (so the `"/path"` string literal is
  1421→  1421→visible), but paren-depth tracking uses the MASKED text (so parens
  1422→  1422→inside strings don't confuse the splitter). For wrapped handlers like
  1423→  1423→`rateLimiter.RateLimitHandler(..., handler.Foo,)`, the LAST
  1424→  1424→`handler.Foo` reference is taken as the actual handler.
  1425→  1425→
  1426→  1426→#### 3. ADMIN_SERVICE_FUNCS set
  1427→  1427→
  1428→  1428→The route classifier only catches HTTP handler names registered on
  1429→  1429→routers — it doesn't catch the underlying service methods they
  1430→  1430→delegate to. For example, `pmHandler.GetFunnel` (registered on
  1431→  1431→`adminAPI`) calls `telemetry.Service.FunnelMetrics(...)`, which is
  1432→  1432→where the actual MongoDB queries live. `ADMIN_SERVICE_FUNCS` is a
  1433→  1433→curated set of these service-method names (FunnelMetrics,
  1434→  1434→CustomEventSummary, EngagementMetrics, RetentionCohorts, KPIs,
  1435→  1435→ListEventTypes, countDistinct, weeklyActiveUsers, monthlyActiveUsers,
  1436→  1436→topCustomEvents, creditConsumptionTrend, medianTimeToFirstPurchase,
  1437→  1437→subscriberTrend, mrrTrend, GetAggregateMetrics, GetCurrentMetrics,
  1438→  1438→GetIntegrationCounts24h, AdminGetMetrics, AdminListTransactions,
  1439→  1439→GetOrCreatePrice, resolveStripeProducts, buildProductNameMap, Load,
  1440→  1440→Reload, Set, Seed). Functions in this set are treated as admin-scoped.
  1441→  1441→
  1442→  1442→#### 4. New Query dataclass fields
  1443→  1443→
  1444→  1444→Each `Query` now records:
  1445→  1445→
  1446→  1446→- `route_scope` — admin | tenant | auth | public | cli | background |
  1447→  1447→  testutil | unknown
  1448→  1448→- `is_admin_handler`, `is_background_task`, `is_public_endpoint`,
  1449→  1449→  `is_auth_flow`, `is_cli_tool` — boolean flags
  1450→  1450→- `collection_has_tenant_id` — None if struct not found, True/False
  1451→  1451→  otherwise
  1452→  1452→- `collection_is_user_scoped` — True if the struct has a `userId` bson
  1453→  1453→  field

A few more angles, these go beyond cleanup into "did we just trade one class of bug for its mirror image":

6. Check the fix for over-matching, not just under-matching

The original bug was the lookup being too strict (missing real matches). The fix adds three fallback strategies, ending in a linear scan. That's the right direction, but linear scan / fuzzy matching by name is exactly the kind of change that can introduce false positives in the opposite direction — e.g. two different structs each having a method called List() or Get(), and the fallback matching the wrong receiver's method to the wrong function node. Worth explicitly testing: does the repo have any two structs with same-named methods ((*AdminHandler).List and (*TenantHandler).List)? If so, confirm the normalized-label matching picks the correct one, not just a one. This matters more than it sounds — a wrong match here silently attributes one function's filter fields to a different function, which is worse than a missing edge because it looks confidently correct.

7. Does the go/types struct-flattener have the same label-matching architecture?

The bug that was found and fixed lived in enrich_with_ssa's function-node lookup. The struct flattener (type_resolves_to edges, 591 of them, from Phase 2) presumably does its own struct-node lookup by label to attach flattened fields. A few more, moving into areas not yet touched:

10. Interfaces and dynamic dispatch

go/ssa tracing works well for concrete method calls, but if any filter-building code goes through an interface (e.g. a Repository interface with multiple concrete implementations), SSA analysis needs to resolve which concrete implementation to trace — this is a classic static-analysis blind spot (interface dispatch is a runtime decision). Worth checking whether any of the 26 functions with map_update findings call through an interface rather than a concrete struct, and whether the tracer either (a) correctly enumerates all possible implementations, or (b) silently picks one / silently skips it.

11. Generics

If EasyClass/LastSaaS uses any Go generics (type parameters), go/types handles these but flattening logic for embedded generic types can be subtly wrong (e.g. a generic wrapper struct embedding T where T is a type parameter — what does "flattened fields" even mean there?). Worth a quick grep -rn "\[T " --include="*.go" . or similar to check if generics are in play at all before assuming this is a non-issue.

12. graph.json vs public/graph.json sync drift

The summary mentions syncing "the enriched graph to public/" as a manual step. That's a second copy of the same data — worth confirming this is an automated part of enrich --all (or a documented always-do-this-after step), not something that can silently drift if someone runs enrichment and forgets the sync. This is the same class of bug as staleness detection (#2 from two turns ago) but for a different pair of files — worth extending that staleness check to cover both copies, or better, making public/graph.json a symlink/build artifact rather than a hand-copied file.

13. Closures and goroutines in the SSA trace

If any filter-building code happens inside a closure or a goroutine (go func() { filter[...] = ... }()), SSA's per-function analysis can lose track of the enclosing function's identity, or attribute the write to an anonymous function node that doesn't map cleanly to anything meaningful in the graph. Worth checking whether any map_update findings got attributed to something like func1 or an unnamed closure rather than a real named function — that would be a sign this case exists and isn't handled cleanly.
